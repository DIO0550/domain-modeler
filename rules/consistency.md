# 整合性規約

`rules/architecture.md` が **依存してよい向き**(誰が誰を import できるか)を規定するのに対して、この規約は **同時に正しくなければならない範囲**(どこまでが一括で整合している必要があるか)と、**その範囲を壊さない更新経路**を規定する。2つは別の軸で、両方を満たす必要がある。

## 整合性境界

**このアプリの整合性境界は開いている1ドキュメント。** 1ドキュメント = 1ファイル(`.dcanvas` / `.dmodel`)で、他のファイルへの参照を持たない。この決定は `docs/domain-modeler/canvas-format.md` / `model-format.md` の「基本原則」で宣言されており、**境界の宣言でもある**。

- `.dcanvas` と `.dmodel` は別々の境界。スキャフォールド生成は一方向・名前ベースで、**ID の相互参照を持たない**(`canvas-format.md` 9)。両者を1つの境界として扱う設計を入れない
- タブが複数開いていても、整合性境界はタブごとに独立している。あるタブの保存失敗が別のタブの内容を壊してはならない

境界の内側で常に成立していなければならないこと。

- `.dcanvas`: 接続線の `from` / `to` が、同じドキュメント内に存在する付箋を指している。`id` が文書内で一意である(`canvas-format.md` 8)
- `.dmodel`: 宣言名が重複していない。型参照の解決は同じドキュメント内で完結する(未定義参照は書き途中として警告に留める — `model-format.md` 9)
- 参照の向きに循環が無い

**部分的に壊れた状態をファイルへ書かない。** 検証を通っていない中間状態を永続化すると、次に読む人(AI・外部エディタ・再起動後の自分)が矛盾したドキュメントを読むことになる。メモリ上でどれだけ整合を作り込んでも、保存が割れていれば意味がない。

## 境界の決め方

新しい型・新しいまとまりを作るとき、**どこまでを1つの塊として扱うか**は次の順で決める。

1. **判定に何が要るか** — その規則が成立しているかを判定するために、同時に見る必要がある値は何か。その最小の集合が塊の候補になる。1つの値で答えが出るなら、それ以上広げない
2. **同時に書き換わると壊れるか** — GUI の編集と外部(AI・エディタ・git 操作)の書き込みは同時に起きうる。どちらか一方が必ず負けるべき範囲はどこか。そこが一括で読み書きする単位になる
3. **無制限に育たないか** — 1箇所の更新のために毎回どれだけ読む必要があるか。件数に上限がない関係を1つの塊に含めない

1〜3 で決まった範囲が、そのまま**一括で更新し、一括で検証する単位**になる。

## 更新の入口

**部分を直接書き換える関数を公開しない。** ドキュメントの深い位置にある付箋・宣言を変更する場合も、入口はルート側のコンパニオンオブジェクト(`Document` など)に置き、**新しいドキュメントを返す**。

- 塊の内部だけを受け取って内部だけを返す更新関数を公開APIから export しない。呼び出し側が整合を取り直す義務を負う形になり、守り忘れが検出できない
- 更新の結果として派生値の作り直しが必要なら、それを行うのはルート側の責務。呼び出し側に再計算を求めない
- 変更後の値は**不変条件を満たしたものだけ**を返す。満たせない入力は `Result` で返し、壊れた値を作って返さない

## 導出を優先する

**同じ情報を二重に持った時点で、整合性の問題が発生する。** 派生する値は保存せず、必要なときに計算する。

保存してよいのは次のどちらかに当てはまるときだけ。

- 計算コストが高く、毎回は回せない(計測した上で判断する)
- **その時点の値を固定したい**(後から元が変わっても、この値は変わってはいけない)

2つ目は整合性ではなくスナップショットの要求なので、「導出できるのに保存している」のではなく「別の値である」ことが分かる名前にする(`lastSavedContents` など)。

**導出できる値をファイルへ書かない。** ファイルが source of truth である以上、ファイル内の二重化は外部編集で即座に矛盾する(`.dcanvas` の `note` が読み込み時に無視され保存時に再生成されるのはこの理由 — `canvas-format.md` 8)。

## 永続化の原子性

- 書き込みは一時ファイル + rename で**アトミック**に行う(`docs/domain-modeler/technical.md` 4)。整合性境界の単位とファイルの単位が一致しているので、これで境界全体の原子性が保てる
- **複数ファイルに跨る保存を導入しない。** 導入する場合は片方だけ書き込みに失敗するケースが生まれるため、この規約全体を見直す必要がある。実装前に相談する
- 自動保存のデバウンス中に落ちた場合、失われるのは最後の編集だけで、**ファイルが壊れることは無い**状態を保つ
- 書き込み経路を feature ごとに散らさない。I/O の呼び出し口は `rules/architecture.md`「I/O の呼び出し口」に従い、`features/<x>/domains/` は副作用を `operations` として受け取る

## 外部変更との整合

外部(AI・エディタ・git 操作)による変更は、こちらの編集と同期しない。ここは**あとで揃う**ことを前提に設計する。

- file watch で変更を検知して再読み込みする(`technical.md` 5)
- 不正な内容だった場合は、最後に正常だった描画を保持してエラーを重ねて表示する。**壊れた内容を取り込んで内部状態を壊さない**
- 未保存編集・未確定の入力下書きと競合する場合の停止規則は `rules/coding.md` に従う(ユーザーが保持する側を選ぶまで自動保存と終了を停止する)
- これは「整合性を諦める」ことではない。外部の編集が正常な内容に直った時点で、必ず揃う経路があることを保証する

## feature の構成とネスト

**feature 同士の参照は公開API(`index.ts`)経由なら可。禁止するのは deep import と循環。**
ネストしても同じ語を使うことで、どの階層でも判断基準が同じになる(子 feature も親と同じルールに従う)。

```
apps/desktop/src/
  appShell/              # 合成役: features を1画面へ並べる
  features/<feature>/
    features/            # この feature からしか使われない子 feature
    components/
    domains/
    hooks/
    index.ts
```

現状このリポジトリの feature は `auto-save` / `canvas` / `model` / `scaffold` の4つがフラットに並び、
相互参照は0件、合成役は `appShell/` が担っている。**親になる feature がまだ無いので、ネストの規則は
feature が増えたとき(ある feature が別の feature からしか使われなくなったとき)に効く。**

### どの階層でも同じルール

| ルール | 内容 |
|---|---|
| 公開API | 各 feature の `index.ts`。**deep import は禁止** |
| 兄弟参照 | **公開API 経由なら可**。循環は禁止 |
| ネスト | 親でしか使わない子は配下へ。**深さは2段まで** |
| 昇格 | 2つ以上の階層から必要とされたら1つ上へ移す。2つ以上の feature が必要とするドメインは `packages/@domain-modeler/*` へ |

深さ2段は `features/<親>/features/<子>/` まで。それ以上が欲しくなったら、切り方を疑う。

### 兄弟参照を禁止しない理由

- **業界標準ではない。** React 公式・Next.js 公式はフォルダ構成に意見を持たない。bulletproof-react も「良い考えではないかもしれない」という提案レベルで、lint 設定例は任意の手段として添えられているだけ。明確に禁止しているのは FSD だけで、そこも entities 層に `@x` という例外を後付けしている
- **禁止すると昇格が強制される。** 参照が発生した瞬間に上の階層(`packages/`)へ押し出すことになり、まだ1つの feature の事情でしかないものが共有物になる。公開API 経由を許せば「2つ以上が必要としたら」まで判断を遅らせられる
- **内部構造を隠す目的は deep import の禁止で達成できている。** 参照そのものの禁止は追加の利益が小さい

この判断は、**`appShell` 以外が合成役を持ち始めたとき**に再検討する。

### ネストしないもの

**ドメイン軸でまとまっている feature はネストしない。** 複数の画面領域に UI を提供していても、同じドメイン・
同じ選択状態に反応して一緒に変わるなら、それは1つのまとまり。使われ方で割ると凝集が壊れる。

参照元が2つ以上ある feature も同じ。ネストすると片方が兄弟参照か孫への deep import になるため、
共通の親の直下に置く。

### 守ること

- **公開API に出すものは最小限に絞る。** `index.ts` から export した時点で契約になり、変更が外に波及する。内部だけで使うものを「便利だから」と export しない
- **循環が生まれたら、それは切り方が間違っているサイン。** 2つが互いを必要とするなら、共有部分を1つ上へ上げるか、1つにまとめる

### 機械的に落とす

規約だけでは守れないので、検査を回す。

**パッケージ境界**は `package.json` の `exports` で塞ぐ。lint より前にモジュール解決が失敗するので、設定を書き忘れても破れない。

```json
{
  "name": "@domain-modeler/canvas-core",
  "exports": { ".": "./src/index.ts" }
}
```

**同一パッケージ内の境界**(feature 間・層間)は `scripts/check-module-boundaries.mjs` が検査する。

```bash
pnpm run check:boundaries
```

- 他 feature の内部への import(`@/features/<x>/domains/...` など)を落とす。エイリアスでも相対パス(`../../<x>/domains`)でも同じルールで落ちる。公開API(`index.ts`)経由の参照は通す
- feature 間の循環参照を落とす(ネストした親子も同じ扱い)
- `features/<親>/features/<子>/` より深いネストを落とす
- `features/<x>/domains/` から `libs/` への import を落とす(I/O の呼び出し口の固定)
- feature を追加・ネストしても設定変更は要らない(`features/` フォルダを実行時に辿る)
- CI(`.github/workflows/frontend.yml`)と push 前フック(`.claude/hooks/pre-push-boundaries.sh`)から実行する

`__tests__/` 同士のフィクスチャ共有は、他 feature のものを deep import せず、各 feature 内のセットアップ関数で閉じる。

## 保留している判断

規約には含めないが、検討して結論を出さなかったもの。再燃したときに同じ議論を繰り返さないために残す。

### 合成をどこに置くか

`appShell/` は自身の骨格(タブ・ファイル操作・外部変更の取り込み)と、feature を並べる合成コードの両方を持っている。
合成を上位へ出す案(`App.tsx` へ移す・専用の層を新設する)は見送った。

- `App.tsx` へ出す → 「エントリ層はロジックを持たない」という既存規約と衝突し、App が新しい合成ハブになるだけ
- 層を新設する → 画面が実質1つのアプリで層を増やす価値が薄い

一般には composition root(page / route 層)で合成するのが定番で、その層を薄く保つことがセットで語られる。
**従属関係が構造に出ていれば、`appShell` が合成を持つこと自体は不自然ではない**と判断した。
再検討のトリガーは「トップレベルの画面が2つ目になったとき」。

## この規約が扱わないこと

- 誰が誰を import してよいか → `rules/architecture.md`
- ロジックをどの型に帰属させるか → `rules/architecture.md`「ロジックの帰属先」
- 何をモックしてよいか → `rules/testing.md`
