# モデル依存図 — 機能仕様書

作成日: 2026-09-28 / 更新日: 2026-10-09 / 対象: DIO0550/domain-modeler / 状態: 実装前提を整理した仕様（機能は未実装）

## 概要

`.dmodel` に記述された `data` と `workflow` をノードとして表示し、宣言間の参照を矢印で可視化する。AIが生成・更新したモデルと人が記述したモデルを同じ仕組みで扱い、構造・依存先・参照元を確認できるようにする。

モデル本文を唯一の正として、既存の解析結果から図を導出する。AIが図用の座標や別の依存情報を書く必要はない。

## 背景と目的

既存の構造化プレビューは宣言ごとの内容を読みやすくする。一方、複数宣言を横断する参照や、ある型を変更した場合に確認すべき宣言は、一覧だけでは追いにくい。

クラス図に似た箱と矢印で構造を示し、選択した宣言の近傍をたどれるようにする。表示対象はドメインの型・処理であり、ソースコード上のクラスや import ではない。

## 合意した方向と実装前提

### 会話で合意した方向

- 既存の `.dmodel` から依存図を自動生成する。
- 「モデル」画面で「定義＋プレビュー」と「依存図」を切り替える。
- 自動配置、依存先・参照元の強調、右側での定義確認、編集画面への移動を備える。
- 選択した宣言と直接つながる宣言だけに絞る操作を備える。
- `data` に加え、`workflow` の入力・出力・エラーへの参照も対象とする。最後の項目は文書作成時の選択回答で確認済み。

### #278で整理した実装前提

後続Issueは次の仕様を前提に進める。本書の更新は既存コード・規約との照合結果であり、個々のUI仕様がユーザー承認済み、または実装・実機検証済みであることは意味しない。

| 論点 | 実装前提 | 理由・確認先 |
| --- | --- | --- |
| 循環禁止の範囲 | モジュールのimport依存に適用。文書内の型参照には図独自の禁止・診断を追加しない | [整合性規約](../../../rules/consistency.md)。既存の参照解決は名前とソース位置を保持し、型参照を再帰展開しない |
| 矢印の方向 | data・workflowとも参照元 → 参照先。workflowの入力も同じ向き | 構文上の参照を表すため。入力・出力・エラーは役割ラベルで区別する |
| 表示状態の保持 | 同じ文書タブの表示・モード往復で保持。閉じて開き直すと既定値へ戻す | 本文・保存形式と表示状態を分け、別タブへ混在させない |
| 直接近傍 | 選択対象に接続する1段の両方向のノードと辺。別ノード選択で追従 | 参照元と依存先をたどるため。推移的な影響分析へ拡張しない |
| 部分ASTと外部変更 | 文書管理が採用した現在の本文を表示。構文診断がある本文も正常な宣言を表示 | [文書同期仕様](./document-sync-spec.md)の採用境界に従う。読み込み失敗と構文診断を区別する |

## スコープ

| 分類 | 初期スコープ |
| --- | --- |
| 入力 | 現在開いている単一 `.dmodel` 文書 |
| ノード | `data` と `workflow`。未定義参照は明示的な補助ノード |
| 関係 | data の型参照、workflow の input / output / error の型参照 |
| 表示 | 宣言種別、構成要素、AND / OR、list / option、制約 |
| 操作 | 選択、直接近傍への絞り込み、全体表示、定義確認、編集画面への移動 |
| 閲覧支援 | 自動配置、パン、ズーム、全体に合わせる |
| 同期 | テキスト編集、Undo/Redo、既存の外部変更取り込み、文書切替に追従 |

- アプリ内AIチャット、LLMへの問い合わせ、AI生成ボタン。
- ソースコードの逆解析、コード生成、複数 `.dmodel` の横断解析・import。
- 図からの宣言編集、線の追加・削除、ノードの手動配置と座標の永続化。
- UML全体のサポート、継承・集約・所有関係の推測。
- state-machine の状態・遷移と依存図との統合。
- 推移的な影響範囲の自動計算、循環依存の警告ルール追加。
- 画像・PDFエクスポート、印刷、AIによる変更履歴の識別。

## ユーザーストーリー

| ID | 利用者 | 行動 | 得られる価値 |
| --- | --- | --- | --- |
| US-01 | モデル作成者 | AIが作った文書を開き、依存図を見る | 複数宣言の構造を把握できる |
| US-02 | レビュー担当者 | 注文を選択し、依存先を見る | 構成要素の不足や参照の意図を確認できる |
| US-03 | モデル変更者 | 顧客情報を選択し、参照元を見る | 修正時に確認すべき宣言が分かる |
| US-04 | 処理設計者 | workflow の入力・出力・エラーをたどる | 処理が使う型を確認できる |
| US-05 | 大きな文書の閲覧者 | 直接の関連だけに絞る | 関心のある範囲を読みやすくできる |
| US-06 | モデル変更者 | 図から定義の編集位置へ移動する | 対象を探し直さず修正できる |

## 処理の流れ

1. 既存の文書管理が `.dmodel` のテキストを取得する。
2. 既存の model-core が解析・参照解決・診断を行う。
3. 解析結果から、表示用ノード・参照・ソース位置を導出する。
4. UIがノード寸法を決め、対象グラフを自動配置する。
5. 選択・近傍表示・定義への移動を行う。
6. 本文が変わると最新の解析結果から再生成する。図の閲覧操作で本文は変えない。

## 品質と完了条件

- 同じ本文から同じ意味のグラフが得られ、表示モードで本文が変化しない。
- 正常な宣言は、他の宣言の解析エラーがあっても確認できる。
- 色だけに頼らず、種類・選択・関係・警告を判別できる。
- 詳細な受入条件は各仕様書末尾に記載する。
- 応答時間の数値目標と検証対象の最大規模は実装計画で測定条件とともに決める。仕様書段階では性能達成を断言しない。

## 用語

| 用語 | 意味 |
| --- | --- |
| 依存 | 宣言内に別の宣言への参照があること。実行順や所有関係は意味しない |
| 依存先 | 選択宣言が直接参照している宣言 |
| 参照元 | 選択宣言を直接参照している宣言 |
| 直接近傍 | 選択宣言と、そこに1本の辺でつながる両方向の宣言 |
| モデルモード | `.dmodel` の data / workflow を扱う既存の画面モード |
| 依存図 | モデルモード内の新しい表示方法 |
