## 1. 責務と非責務

### 責務

- 字句解析: テキストをトークン列に分解する(ハイライト表示の情報源)
- 構文解析: トークン列からASTを構築する。構文規則は model-format.md に従う
- 参照解決: 名前ベースの定義表・参照表の構築と、未定義参照の検出
- 診断: パースエラーと警告を位置情報付きで報告する
- 編集支援の下地: 識別子の全出現位置の列挙(リネーム・ジャンプが利用)

### 非責務

- 表示・カード描画・エディタ挙動(model-editor)
- ファイルI/O・保存(technical.md)
- テキストの整形(フォーマッタは持たない。テキストは書かれたままが真実)

依存方向は UI → core の一方向。core は純TypeScriptで、DOM・React・Tauri APIに依存しない。

## 2. モジュール分割

以下の関心事を独立したモジュールとして分割する(ファイル・関数の命名は実装の裁量):

- **字句解析**: 行の分類(宣言行・継続行・コメント・空行)とトークン化
- **構文解析**: 宣言単位のAST構築とエラー回復
- **参照解決**: 定義表・参照表・未定義検出
- **型定義**: トークン・AST・診断の型

公開APIは単一の入口に集約し、UI層はそれ以外から import しない。

## 3. パースの性質

- **全文パース**: 入力のたびにテキスト全体を解析し直す。行指向で文法が小さいため、実用サイズ(数千行)では毎回の全文パースで十分とし、インクリメンタルパースは行わない
- **一度のパースで全部返す**: 結果は「AST + トークン列 + 診断リスト」の一組。UIはこれだけで描画・ハイライト・警告表示のすべてを賄う
- **決してエラーで止まらない**: どんな入力に対しても必ず結果を返す。壊れた入力はASTから欠け、診断に載る

## 4. エラー回復

書き途中の文書を常に扱えることを最優先とする。

- **宣言単位で独立に解析する**: インデントのない `data` / `workflow` 開始行を同期ポイントとし、ある宣言の構文が壊れていても次の宣言の解析は影響を受けない
- 壊れた宣言は「エラー宣言」としてASTに位置だけ残し(model-editor 4.3 のプレースホルダ表示に対応)、診断にエラーを積む
- 同期ポイントに到達できない行(どの宣言にも属さない行)は、直前のエラー宣言の範囲に含める

## 5. AST

- 宣言は出現順のリストとして持つ(文書構造がフラットなため、木は宣言内部のみ)
- data宣言は4分類のいずれか: 単一参照 / 直積(AND) / 直和(OR) / 制約付き。model-editor のカード分類(ALIAS / RECORD / CHOICE / VALUE)と1対1に対応する
- workflow宣言は input(AND連結)/ output(OR連結)/ error(OR連結・任意)の3部
- 型参照の項は「名前 + 後置修飾の列 + プリミティブか否か」を持つ
- **全ノードが位置情報(行・桁の範囲)を持つ**。ジャンプ・リネーム・エラー表示はすべてこの位置情報に依拠する

## 6. 診断

| 深刻度 | 対象 | 例 |
| --- | --- | --- |
| エラー | 構文違反 | 宣言の形が不正、AND / OR の混在、範囲の下限 > 上限、`input:` 行の欠落、行順序違反 |
| エラー | 意味違反 | 同名 `data` の再宣言、予約語を識別子に使用 |
| 警告 | 未定義参照 | 定義されていない識別子への型参照(model-format.md 9) |

- 診断は位置情報 + 人が読めるメッセージ(日本語)を持つ
- 診断があってもパース結果は返る(3 参照)。保存も妨げない(model-editor 5.1)

## 7. 参照解決

- **定義表**: 識別子 → 宣言(data / workflow)。data と workflow は同じ名前空間とする(同名の data と workflow もエラー)
- **参照表**: 識別子 → 全出現位置のリスト(宣言名・型参照の両方。コメント内は含めない)
- プリミティブ型・予約語は参照解決の対象外
- 前方参照可。解決は全文パース後に一括で行う
- リネームは「参照表が返す全位置を新しい名前で置換する」操作として model-editor が実現する。core は位置の列挙までを担い、テキストの書き換えはしない

## 8. テスト方針

- Vitest。DOM非依存
- 字句・構文・診断は表駆動テスト(入力テキスト → 期待するAST/診断のペア)
- エラー回復の検証を重視する: 「壊れた宣言の次の宣言が正しく解析されること」「どんな入力でも例外で落ちないこと」
- model-format.md の全構文例をそのままテストケースに含める(仕様と実装の乖離防止)

## 9. スコープ外

- フォーマッタ(整形・インデント正規化)
- インクリメンタルパース、構文木の差分更新
- 入力補完エンジン
- 未使用定義の検出(警告の追加は必要になってから)
- `.dmodel` 同士の import・複数ファイル解決
