## 1. 責務と非責務

### 責務

- 字句解析: テキストをトークン列に分解する(ハイライト表示の情報源)
- 構文解析: トークン列からASTを構築する。構文規則は model-format.md に従う
- 参照解決: 名前ベースの定義表・参照表の構築と、未定義参照の検出
- 診断: パースエラーと警告を位置情報付きで報告する
- 編集支援の下地: 識別子の全出現位置の列挙(リネーム・ジャンプが利用)

### 非責務

- 表示・カード描画・エディタ挙動(model-editor)
- ファイルI/O・保存(technical.md)
- テキストの整形(フォーマッタは持たない。テキストは書かれたままが真実)

依存方向は UI → core の一方向。core は純TypeScriptで、DOM・React・Tauri APIに依存しない。

## 2. モジュール分割

以下の関心事を独立したモジュールとして分割する(ファイル・関数の命名は実装の裁量):

- **字句解析**: 行の分類(宣言行・本文行・コメント・空行)とトークン化。`state-machine`、`initial:`、`state:`、`transition:`、`on`、`terminal` と遷移矢印 `->` を認識する
- **構文解析**: 宣言単位のAST構築とエラー回復
- **参照解決**: トップレベルの定義表と、マシン単位の状態定義表・参照表・未定義検出
- **型定義**: トークン・AST・診断の型

公開APIは単一の入口に集約し、UI層はそれ以外から import しない。

## 3. パースの性質

- **全文パース**: 入力のたびにテキスト全体を解析し直す。行指向で文法が小さいため、実用サイズ(数千行)では毎回の全文パースで十分とし、インクリメンタルパースは行わない
- **一度のパースで全部返す**: 結果は「AST + トークン列 + 診断リスト」の一組。UIはこれだけで描画・ハイライト・警告表示のすべてを賄う
- **決してエラーで止まらない**: どんな入力に対しても必ず結果を返す。壊れた入力はASTから欠け、診断に載る

## 4. エラー回復

書き途中の文書を常に扱えることを最優先とする。

- **宣言単位で独立に解析する**: インデントのない `data` / `workflow` / `state-machine` 開始行を同期ポイントとし、ある宣言の構文が壊れていても次の宣言の解析は影響を受けない
- 壊れた宣言は「エラー宣言」としてASTに位置だけ残し(model-editor 4.3 のプレースホルダ表示に対応)、診断にエラーを積む
- 同期ポイントに到達できない行(どの宣言にも属さない行)は、直前のエラー宣言の範囲に含める
- state-machine の**ヘッダー**(`state-machine <名前> =`)が不正なら宣言全体をエラー宣言にする。ヘッダーが有効なら、本文の1行が不正でもその行を診断して読み飛ばし、同一マシンの後続行を解析し続ける。正常な状態・遷移は部分的なマシンASTに残す
- 本文の回復ポイントは次のインデントされた `initial:` / `state:` / `transition:` 行、次の非インデントのトップレベル宣言行、またはEOFとする。`->` の後で改行した不完全な遷移や未知の本文行は、その行で構文エラーとし、別行のトークンを補充しない。空行・コメントは読み飛ばす
- 正常行から構築した部分ASTに意味診断を適用する。欠けた構文ノードは参照解決せず、架空の状態や遷移を補わない。診断があってもソースの保存と別モードの解析を妨げない

## 5. AST

- 宣言は出現順のリストとして持つ(文書構造がフラットなため、木は宣言内部のみ)
- data宣言は4分類のいずれか: 単一参照 / 直積(AND) / 直和(OR) / 制約付き。model-editor のカード分類(ALIAS / RECORD / CHOICE / VALUE)と1対1に対応する
- workflow宣言は input(AND連結)/ output(OR連結)/ error(OR連結・任意)の3部
- state-machine宣言は名前、状態の出現順の列、遷移の出現順の列を持つ。各状態は `name`・`nameRange`・`initial`・`terminal`・`range` を持ち、`initial:` の参照先の状態だけ `initial: true` とする。遷移は `from`・`fromRange`・`to`・`toRange`・`event`・`eventRange`・`range` を持つ。初期行の位置は診断・ジャンプのために保持する(実装上のノード形状は任意)
- マシンヘッダーや構文上の不完全行を除き、意味エラーがあっても状態と遷移のノードは捨てない。グラフは参照解決済みの有効な状態・遷移のみ描画し、未定義端点や終端からの無効な遷移は表示用辺に投影しない。エディタには元のテキストと診断を残す
- 型参照の項は「名前 + 後置修飾の列 + プリミティブか否か」を持つ
- **全ノードが位置情報(行・桁の範囲)を持つ**。ジャンプ・リネーム・エラー表示はすべてこの位置情報に依拠する

## 6. 診断

| 深刻度 | 対象 | 例 |
| --- | --- | --- |
| エラー | 構文違反 | 宣言の形が不正、AND / OR の混在、範囲の下限 > 上限、`input:` 行の欠落、行順序違反 |
| エラー | 意味違反 | 同名 `data` の再宣言、予約語を識別子に使用 |
| 警告 | 未定義参照 | 定義されていない識別子への型参照(model-format.md 10) |
| エラー | マシン構文 | 不正なヘッダー、項目の不足・余剰、非インデントの本文、未知の項目、予約語を名前に使用 |
| エラー | マシン意味 | トップレベル名・同一マシン内の状態名の重複、初期行0/2行以上、状態0件、未定義の状態参照、終端からの遷移、同一の遷移の重複 |

- 診断は位置情報 + 人が読めるメッセージ(日本語)を持つ
- 診断があってもパース結果は返る(3 参照)。保存も妨げない(model-editor 5.1)
- state-machine では位置を次のようにする。重複マシン名は後のヘッダー名、重複状態名は後の `state:` 名、重複初期行は後の `initial:`、欠落した初期行・状態はマシン名、未定義参照は `initial:` の値または遷移端点、終端からの遷移は遷移元、重複遷移は後の遷移行。構文エラーは問題のトークン、欠落トークンはその行末(または項目マーカー)を指す
- 構文エラーと意味エラーは `error`、未定義の**型**参照のみ `warning`。状態の未定義はグラフの辺を成立させられないため `error`

## 7. 参照解決

- **定義表**: 識別子 → 宣言(data / workflow / state-machine)。3種は同じトップレベル名前空間とする。状態名の定義はマシン別に持ち、同名でもマシンが異なれば別の定義とする
- **参照表**: トップレベルの名前 → 宣言名・型参照の全出現位置。状態の参照表はマシンごとに状態名 → `state:` 宣言名・`initial:` 値・遷移元/先の出現位置。コメントとイベント名は参照に含めない。トップレベル名のリネームで同名の状態やイベントを変えない
- プリミティブ型・予約語は参照解決の対象外
- 前方参照可。解決は全文パース後に一括で行う
- 同じ名前の複数の定義がある場合は先頭を解決先とし、後続の宣言に重複エラーを出す。初期状態は `initial:` の参照を解決して該当する `StateDecl` に印を付ける。重複初期行がある場合は最初の行のみを採用する
- リネームは「参照表が返す全位置を新しい名前で置換する」操作として model-editor が実現する。core は位置の列挙までを担い、テキストの書き換えはしない

## 8. テスト方針

- Vitest。DOM非依存
- 字句・構文・診断は表駆動テスト(入力テキスト → 期待するAST/診断のペア)
- エラー回復の検証を重視する: 「壊れた宣言の次の宣言が正しく解析されること」「どんな入力でも例外で落ちないこと」
- model-format.md の全構文例をそのままテストケースに含める(仕様と実装の乖離防止)
- state-machine は複数マシン・既存宣言との混在・前方参照・複数入出力・自己ループ・初期かつ終端・同一イベントの別遷移・名前衝突・不完全行から次行への回復を検証する

## 9. スコープ外

- フォーマッタ(整形・インデント正規化)
- インクリメンタルパース、構文木の差分更新
- 入力補完エンジン
- 未使用定義の検出(警告の追加は必要になってから)
- `.dmodel` 同士の import・複数ファイル解決
